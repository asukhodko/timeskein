# ADR-0001: Начальная архитектура Timeskein для MVP “Инвентарь текущей работы”

## Статус

**Принято** (для MVP).  
Дальнейшие ADR уточняют/расширяют решения, но не ломают базовый каркас.

## Контекст

Timeskein должен начать приносить пользу с минимальным объёмом реализации и минимальными рисками приватности.

Цель MVP: научиться отвечать на вопрос:

> “Какие задачи/проекты/вопросы сейчас актуальны и какое их состояние?”

При этом архитектура должна:
- быть **local-first** (работать без сервера),
- не требовать “тяжёлого” сбора (видео/аудио) по умолчанию,
- оставлять пространство для будущих функций (эпизоды, нити, синхронизация, семантический поиск, коннекторы).

## Решение

### 1) Локальный агент как главный компонент (Local-first)

Система состоит из **локального агента**, который:
- собирает минимальные сигналы рабочего контекста,
- сохраняет их в локальное хранилище,
- поддерживает “реестр” Work Items и отвечает на запросы UI.

Сервер — **опционален** и не требуется для MVP.

### 2) Данные строятся вокруг двух журналов + устойчивых сущностей

В MVP вводятся:

- **ContextEvent log** (append-only): нормализованные события контекста (активное окно, URL вкладки, переключения, idle и т.п.).
- **WorkItem**: сущность “элемент работы” (task/project/question).
- **WorkItemEvent log** (append-only): изменения состояния/заметок/привязок WorkItem.

Ключевая идея: мы сохраняем “факты” (события) и “человекочитаемое состояние” (WorkItem), а производные представления (например, “актуальные”) вычисляем по правилам.

### 3) Хранилище: SQLite как единая локальная база

Для MVP используется SQLite как встроенное хранилище:
- низкий порог внедрения,
- атомарность,
- индексы для быстрых запросов,
- возможность будущего расширения (FTS, дополнительные таблицы).

В MVP **не требуется** отдельная БД/сервер.

### 4) Сбор сигналов (Collectors): минимум, но достаточно

MVP-коллекторы:
- **Active window**: приложение + заголовок окна.
- **Browser context**: URL + title активной вкладки (через расширение или OS-интеграцию).
- (Опционально) **AFK/idle**: для корректной “актуальности” по времени.

Скриншоты/аудио/полные тексты страниц **не собираются по умолчанию**.

### 5) Привязки к “миру” через Refs (сильные якоря)

Для устойчивого сопоставления контекста и Work Items вводится слой **Refs**:
- URL, домен, пути, идентификаторы документов;
- регулярные выражения для “сильных ключей” (например, `ABC-123`, `repo#issue`, `pull/123`).

Автоматическое создание Work Items из слабых сигналов **не является обязательным**: MVP отдаёт приоритет ручному подтверждению/привязке.

### 6) UI/операции: ручное состояние как источник истины

Состояние Work Item (`active|waiting|blocked|done|someday|unknown`) задаётся пользователем быстрыми действиями (hotkeys/панель).

Автоматическая логика может вычислять `focus_now` (что открыто сейчас), но не должна бесконтрольно переписывать `state`.

### 7) Приватность и политики — “по умолчанию строго”

В MVP вводятся базовые правила:
- allow/deny список приложений/доменов,
- режим “pause”,
- хранение только метаданных контекста,
- удаление Work Item должно удалять связанные события/привязки в пределах политики.

Сложные политики редакции (PII), уровни чувствительности и E2EE не блокируют MVP, но архитектура допускает их добавление как отдельного слоя (Policy Gate).

## Последствия

### Плюсы
- Быстро даёт первую ценность без тяжёлой инфраструктуры.
- Данные устойчивы (refs) и объяснимы.
- Есть естественный путь развития к Episodes/Threads (через журналы событий).
- Минимальные риски приватности (нет “толстых” артефактов).

### Минусы / компромиссы
- Качество “структурированности” в MVP зависит от ручных действий пользователя.
- Без коннекторов глубина контекста ограничена заголовками и URL.
- “Нити” и “эпизоды” не появятся сами — это следующий слой.

## Рассмотренные альтернативы

1) **Сразу делать Episodes/Threads как базовую сущность**  
   Отклонено: переусложнение и высокий риск “не довести до полезного”.

2) **Полная автоклассификация задач и состояний по заголовкам/LLM**  
   Отклонено для MVP: ошибки подрывают доверие; к тому же требует тонкой политики приватности.

3) **Сервер обязателен (центральный индекс/поиск)**  
   Отклонено: противоречит local-first и усложняет запуск.
