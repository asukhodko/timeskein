# ADR-0001: Начальная архитектура Timeskein для MVP "Инвентарь текущей работы"

## Статус

**Принято** (для MVP Level 0).  
Уточнено [ADR-0002](0002-mvp-manual-first.md): MVP = Manual-first.

## Уровень зрелости

**Level 0** (Manual-first) — базовая архитектура.  
Level 2/3 — заложенные расширения.

## Контекст

Timeskein должен начать приносить пользу с минимальным объёмом реализации и минимальными рисками приватности.

Цель MVP: научиться отвечать на вопрос:

> "Какие задачи/проекты/вопросы сейчас актуальны и какое их состояние?"

При этом архитектура должна:
- быть **local-first** (работать без сервера),
- не требовать "тяжёлого" сбора (видео/аудио) по умолчанию,
- **не требовать фонового наблюдения в MVP** (Manual-first),
- оставлять пространство для будущих функций (эпизоды, нити, синхронизация, collectors).

## Решение

### Принято для Level 0 (MVP Manual-first)

#### 1) Локальный агент как главный компонент (Local-first)

Система состоит из **локального агента (TS-AGENT)**, который:
- хранит данные в локальном хранилище,
- поддерживает реестр Work Items,
- отвечает на запросы Surface (UI).

Сервер — **опционален** и не требуется для MVP.

Текущая macOS-реализация 2026-06-30 запускает agent embedded внутри Tauri-процесса, но сохраняет архитектурную границу: UI общается с agent через Local API, а не через прямой доступ к SQLite.

#### 2) Данные строятся вокруг WorkItem и его журнала

В MVP Level 0 вводятся:

- **WorkItem**: сущность "элемент работы" (task/project/question).
- **WorkItemEvent log** (append-only): изменения состояния/заметок/привязок WorkItem.
- **Refs**: привязки к внешнему контексту (URL, файл, ключ тикета).

Ключевая идея: сохраняем "факты" (события) и "человекочитаемое состояние" (WorkItem), производные представления вычисляем по правилам.

#### 3) Хранилище: SQLite как единая локальная база

Для MVP используется SQLite как встроенное хранилище:
- низкий порог внедрения,
- атомарность,
- индексы для быстрых запросов,
- возможность будущего расширения (FTS, дополнительные таблицы).

#### 4) Привязки к "миру" через Refs (сильные якоря)

Для устойчивого сопоставления контекста и Work Items вводится слой **Refs**:
- URL, домен, пути, идентификаторы документов;
- регулярные выражения для "сильных ключей" (например, `ABC-123`, `repo#issue`, `pull/123`).

В MVP Level 0 refs добавляются **вручную** (paste/выбор файла/ручной ввод).

#### 5) UI/операции: ручное состояние как источник истины

Состояние Work Item (`active|waiting|blocked|done|someday|unknown`) задаётся пользователем быстрыми действиями.

`last_seen` обновляется **только по явным действиям пользователя** в Timeskein (touch/edit/open/state/note/ref change).

#### 6) Приватность — "по умолчанию строго"

В MVP Level 0:
- **Нет фонового наблюдения** (нет collectors),
- Refs добавляются только явным действием пользователя,
- Базовый denylist доменов для URL refs,
- Хранение только метаданных, введённых пользователем.

### Заложено для Level 2/3 (будущие расширения)

#### A) ContextEvent log (Level 2+)

Append-only журнал событий внешнего контекста:
- активное окно (app_id, window_title),
- URL вкладки (через расширение браузера),
- idle/AFK события.

**Не является частью MVP Level 0.**

#### B) Collectors (Level 3)

Источники событий, работающие в фоновом режиме:
- **Active window watcher** — приложение + заголовок окна,
- **Browser context** — URL + title активной вкладки,
- **AFK/idle** — для корректной "актуальности" по времени.

**Требуют системных разрешений. Не являются частью MVP Level 0.**

#### C) Connectors (Level 2)

Источники событий, работающие по явному действию:
- "Захватить текущий контекст" как команда,
- Интеграции с приложениями (GitHub, Slack).

**Требуют разрешений конкретных источников.**

#### D) Episodes и Threads (Level 2+)

Производные представления из ContextEvent log:
- **Episodes** — интервалы с единым контекстом,
- **Threads** — сквозные темы, связывающие эпизоды.

**Строятся поверх ContextEvent, не являются частью MVP Level 0.**

---

### Принципы безопасности источников (для Level 2+)

#### Pairing/Allowlist

Новый источник событий (SourceNode) не начинает кормить память, пока его явно не одобрили:
- Пользователь должен явно разрешить каждый источник,
- Источник получает токен/идентификатор при одобрении,
- Список одобренных источников хранится в агенте.

#### Revocation

При отзыве доверия к источнику:
- Источник отключается от агента,
- Все данные с его provenance могут быть удалены,
- Пользователь подтверждает удаление.

#### Permissions per Source

Каждый источник объявляет требуемые разрешения:
- Какие типы событий он генерирует,
- Какие системные разрешения нужны,
- Какой уровень чувствительности данных по умолчанию.

## Последствия

### Плюсы
- Быстро даёт первую ценность без тяжёлой инфраструктуры.
- **Минимальные риски приватности** в MVP (нет фонового сбора).
- Данные устойчивы (refs) и объяснимы.
- Есть естественный путь развития к Episodes/Threads (через журналы событий).

### Минусы / компромиссы
- Качество "структурированности" в MVP зависит от ручных действий пользователя.
- Без collectors глубина контекста ограничена тем, что пользователь вводит сам.
- "Нити" и "эпизоды" не появятся в MVP — это следующий слой.

## Рассмотренные альтернативы

1) **Сразу делать Episodes/Threads как базовую сущность**  
   Отклонено: переусложнение и высокий риск "не довести до полезного".

2) **Включить минимальные collectors в MVP**  
   Отклонено: требует системных разрешений, усложняет приватность. См. [ADR-0002](0002-mvp-manual-first.md).

3) **Сервер обязателен (центральный индекс/поиск)**  
   Отклонено: противоречит local-first и усложняет запуск.

## Расширение: Evidence-Mode (Level 3)

**Evidence-Mode** — строго opt-in функция Level 3 для захвата screen evidence chunks и их дистилляции в Timeline Cards/Episodes.

Это расширение базовой архитектуры, которое:
- Не меняет Manual-first философию (Work Items остаются источником истины)
- Добавляет новый тип SourceNode (Screen Evidence Collector)
- Требует явного включения пользователем

См. [ADR-0003: Evidence-Mode Opt-in](0003-evidence-mode-opt-in.md) для деталей.
