# 0) Что перепроверено и что нужно поправить в моих прошлых выводах

## Главная находка ревизии: в документах Timeskein сейчас два “центра гравитации” MVP

1. Линия **“минимальные коллекторы контекста уже в MVP”**:

* `docs/00_project_overview.md` описывает MVP как инвентарь, обновляемый “автоматически по контексту (окна/URL) и вручную”.
* `docs/adr/0001-initial-architecture.md` в MVP закладывает `ContextEvent log`, watcher активного окна, browser context.
* `docs/mvp/01_user_story_inventory.md` тоже про “создать/привязать из текущего контекста”.

2. Линия **“Manual-first MVP без фонового наблюдения”**:

* `docs/mvp/02_user_story_manual_inventory.md` и `docs/mvp/02_manual_inventory_ui_ux.md` прямо фиксируют “никакого фонового наблюдения, только явные действия пользователя”.
* `docs/roadmap/0001-mvp-execution-roadmap.md` и зрелостная модель в `docs/rfc/0003-client-app-suite-architecture.md` поддерживают именно manual-first как старт.

Это не мелкая разница, а **разные философии доверия/разрешений/сбора**. Поэтому миграция документов должна в первую очередь **устранить двоевластие MVP**.

## Коррекция моих прошлых тезисов про “Gateway”

Я раньше сказал “централизованный Gateway не нужен”. После чтения RFC‑0002/0003 уточнение такое:

* В Timeskein уже есть правильная сущность “Gateway‑по‑смыслу” — это **TS‑AGENT (Device Agent)**: центральная точка правды на устройстве, куда приходят UI и события.
* Значит, “заимствование Gateway” из Clawdbot не про добавление нового компонента, а про **явное описание контрольной плоскости агента**: health/status, управление источниками событий, разрешениями, пайрингом, паузой, диагностикой, плановыми задачами.

# 1) Целевая версия документации (куда мигрируем)

## Цель миграции

Сделать документацию Timeskein **внутренне непротиворечивой** и пригодной как ТЗ/спека для реализации контуров памяти:

* **Контур “Memory Ingest”**: как источники (collectors/connectors) поставляют факты, какие гарантии, как устроены разрешения, провенанс, доверие.
* **Контур “Memory Distillation & Retention”**: как сырые события и артефакты превращаются в эпизоды/нити/итоги, и как данные “забываются” безопасно (TTL, редукция, удаление).
* **Контур “Manual-first как базовый режим доверия”**: всегда работает, почти без разрешений, остаётся полезным при появлении автоматизации.

## Результат миграции документов

Документация после переработки должна:

1. Ясно разделять **режимы зрелости** (как в RFC‑0003):

* Level 0: Manual-first
* Level 1: Sync
* Level 2: Semantics-first connectors (явные действия / минимальные разрешения)
* Level 3: Full context collectors (always-on по включению пользователя)

2. Ясно разделять **плоскости**:

* **Data plane**: канонические события/артефакты/сущности, как они хранятся.
* **Control plane**: кто имеет право отправлять события, какие capabilities, как включается/отключается сбор, как проверяется здоровье.

# 2) Какие заимствования из Clawdbot реально “заходят” в Timeskein

Ниже — финальный список, уже “приземлённый” на текущие документы Timeskein.

## Берём (встроить в доки как опорные принципы)

### A) “Источники как Nodes” (Collectors/Connectors → Source Nodes)

**Что берём:** декларативная модель источников: каждый источник объявляет возможности, типы событий, требования разрешений.
**Зачем Timeskein:** без этого сбор контекста превращается в зоопарк интеграций без единой политики.
**Как назвать в Timeskein:** `SourceNode` (или `EventSource`) с **manifest**.

**Приземление на текущие доки:** RFC‑0002 уже описывает Collectors/Connectors как источники событий, но не формализует их контракт. Мы добавляем формализацию.

### B) Pairing/Trust model для всех источников событий

**Что берём:** “новый источник не начинает кормить память, пока его явно не одобрили”, плюс отзыв и удаление по provanance.
**Зачем Timeskein:** это прямое продолжение принципов “приватность и контроль” и “провенанс”.

**Приземление:** RFC‑0002 задаёт “device identity” как открытую тему — миграция документации должна закрыть её хотя бы на уровне протокола/терминов.

### C) Агент как “control plane”, не только как БД и use-cases

**Что берём:** агент — это долгоживущий демон, который:

* принимает события,
* применяет политики,
* ведёт состояние источников,
* даёт health/status,
* управляет паузой/denylist,
* запускает плановые задачи дистилляции.

**Приземление:** RFC‑0003 уже говорит “agent должен жить постоянно”; теперь это надо усилить описанием контрольной плоскости.

### D) “Distill before forget” (memory flush перед удалением/TTL)

**Что берём:** перед тем как выкинуть сырьё (скрины/сырые эвенты/тяжёлые артефакты), агент обязан сделать выжимку/обновить эпизоды/нити.
**Зачем Timeskein:** иначе “минимизация данных” будет убивать память.
**Приземление:** прямо в философию Timeskein (минимум данных + способность отвечать).

### E) Schema-first на границах (contracts + валидация + codegen)

**Что берём:** строгие схемы сообщений на:

* Local API (Surface ↔ Agent)
* Event Ingest (Sources → Agent)
* Sync (Agent ↔ Hub)

**Приземление:** TS‑SCHEMA уже описан в RFC‑0002 — нужно превратить это из лозунга в ТЗ на структуру контрактов/версий/совместимости.

### F) Артефакт‑пайплайн с TTL и предсказуемыми лимитами

**Что берём:** lifecycle для артефактов: тонкий индексируемый слой + опциональный “толстый слой” с TTL, лимитами, GC.
**Приземление:** сейчас “артефактов почти нет” в MVP — но документация должна заранее описать правила, чтобы потом не поломать доверие.

## Не берём в ядро (оставляем как дальнюю опцию/паттерн)

### G) “Session routing / dmScope / identityLinks” как обязательную часть сейчас

Это полезно для коннекторов мессенджеров, но:

* в Timeskein MVP и ближайших RFC важнее “контекст задач”, а не “контекст людей”,
* иначе распухнет объём спецификаций.

**Что сделать вместо:** заложить “место” в модели сущностей под identity linking (как future RFC), но не тащить в текущую миграцию как обязательный блок.

# 3) Принципы новой редакции документации Timeskein

Это не “ещё одна философия”, а **нормативные правила**, которые должны появиться в docs как требования.

## 3.1. Единственная точка правды на устройстве — TS‑AGENT

* Surfaces не хранят истину и не реализуют правила.
* Sources не пишут в БД напрямую.
* Любая политика приватности/редакции применяется на входе в Agent (или дублируется на source, но агент — финальный арбитр).

## 3.2. Manual-first — базовый режим доверия и работоспособности

* Всегда работает “без разрешений уровня слежки”.
* Любой “богатый контекст” добавляется как **опциональный слой**, включаемый пользователем.

## 3.3. Любой источник событий должен быть:

* идентифицирован (source_id, version),
* одобрен (pairing/allowlist),
* ограничен (capabilities/permissions),
* наблюдаем (health/status),
* отзывчив (revocation + удаление данных по provenance).

## 3.4. Данные делятся на:

* **Canonical** (события/журналы) — append-only, объяснимые,
* **Derived** (эпизоды/нити/итоги/индексы) — пересчитываемые,
* **Ephemeral** (тяжёлые артефакты) — с TTL.

## 3.5. “Distill before forget”

Нельзя удалять/сжимать сырые данные без:

* обновления эпизодов/нитей,
* фиксации “итогов/выводов/следующих шагов” (если включено),
* записи провенанса “что было дистиллировано и чем”.

## 3.6. Контракты версионируются, совместимость — описана

* TS‑SCHEMA задаёт DTO и версии.
* Local API и Ingest API должны иметь тесты контрактов.

# 5) Новые документы, которые нужно добавить (как часть миграции)

Это ключ к “памяти/контексту”. Без этих RFC дальше получится каша.

## 5.1. ADR: “MVP = Manual-first (Level 0)”

**Зачем:** зафиксировать решение, которое сейчас размазано по нескольким документам.
**Содержимое:** кратко, без деталей реализации — только “что считаем MVP”.

## 5.2. RFC: “Local API (Surface ↔ Agent)”

**Зачем:** сейчас это описано как идея, но не как контракт.
**Обязательные разделы:**

* transport требования (без фиксации технологии)
* DTO и ошибки (validation/conflict/privacy_blocked/not_found)
* subscriptions/notifications (как UI узнаёт об изменениях)
* security: только локально, не слушать наружу

## 5.3. RFC: “Event Ingest + SourceNode model + Pairing”

**Это сердце заимствований из Clawdbot.**
**Обязательные разделы:**

* SourceNode manifest (id, version, caps, permissions, event types, sensitivity defaults)
* pairing flow (approve/reject, token issuance, allowlist)
* revocation (отключение + удаление данных по provenance)
* event envelope (idempotency key, timestamps, device_id, source_id, policy decisions)
* health/status источников

## 5.4. RFC: “Retention, TTL и Distillation pipeline”

**Зачем:** “минимизация данных” должна быть инженерно реализуемой, иначе это лозунг.
**Обязательные разделы:**

* слои данных (canonical/derived/ephemeral)
* TTL правила по уровням чувствительности
* distill-before-forget: что генерируем перед удалением
* GC и аудит удаления
* настройки пользователя и провенанс применённых правил

# 6) Редакционные правила для всей документации (чтобы не расползалось снова)

1. Каждый документ должен иметь:

* **Status** (Draft/Accepted/etc.)
* **Scope / Non-goals**
* **Связанные документы** (обязательные ссылки)
* Явную маркировку: **какой уровень зрелости** (Level 0/1/2/3)

2. Термины — один раз в словаре, потом только ссылки:

* `Event`, `Artifact`, `WorkItem`, `Ref`, `Episode`, `Thread`, `Mark`
* `SourceNode`, `PolicyGate`, `Provenance`, `Distillation`, `Retention/TTL`

3. Нельзя смешивать в одном MVP‑доке:

* manual-first требования
  и
* always-on collectors как “вроде бы тоже MVP”
  Без явного “Extension / Future level”.

# 8) Definition of Done для миграции документации

Миграция считается завершённой, если:

1. **Нет противоречий**: MVP везде означает одно и то же (Level 0 manual-first).
2. У каждой “магии автоконтекста” есть маркировка: Level 2/3 + dependency на RFC Ingest/SourceNodes.
3. Появились три “контрактные” оси:

   * Local API
   * Event Ingest + trust/pairing
   * Retention/TTL + distillation
4. В каждом месте, где появляются автоматические данные, описан:

   * provenance
   * политика приватности
   * отзыв/удаление
