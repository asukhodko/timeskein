# Periodic Report Dogfood

## Статус

**P0, профили, Reflection Sessions, семантический Track-слой и evidence-backed Track story приняты 2026-07-10.** Периодический отчёт построен на реальной локальной базе за 1–9 июля 2026 года; недельный и Track-обзоры сохранены как Reflection Sessions и повторно прочитаны отчётом. Новый real-data срез 10 июля подтвердил typed evidence, исторические Ref snapshots и follow-up решений.

Сырые Markdown/JSON-выгрузки остаются локальными и не коммитятся: они содержат имена людей, внутренние URL, рабочие события и личные заметки.

## Проверенный сценарий

```bash
pnpm report:period -- --from 2026-07-01 --to 2026-07-10 --format md \
  --output /tmp/timeskein-period-report-2026-07-01--2026-07-09.md

pnpm report:period -- --from 2026-07-01 --to 2026-07-10 --format json \
  --output /tmp/timeskein-period-report-2026-07-01--2026-07-09.json
```

`--from` включается, `--to` не включается. Поэтому верхняя граница `2026-07-10` включает в обзор весь день 9 июля.

## Фактура

- 9 календарных дней, 7 дней с фокус-блоками;
- `39:53:26` учтено;
- `37:19:24` рабочей занятости;
- `35:14:09` исполнительной работы;
- `2:34:02` вне работы;
- 105 входов;
- 28 событий дня;
- 16 смысловых событий дел;
- 5 captures: 3 превращены в дела, 2 закрыты, открытых нет;
- 19 крупных разрывов между блоками;
- 10 разрывов получили классификацию, 9 старых разрывов остались без объяснения.

Markdown и JSON построены из одного объекта отчёта. Верхняя граница периода проверена: блок, начинающийся ровно в `--to`, в отчёт не попадает.

## Что стало видно

1. Ранние dogfood-дни содержат много времени, но мало смысловых событий и почти не используют Activity Zones. Отчёт явно показывает эту разницу в качестве данных вместо того, чтобы молча сравнивать все дни как одинаково надёжные.

2. Несколько Work Items используются как широкие контейнеры на протяжении нескольких дней или в разных зонах. Они удобны для текущего трекинга, но недостаточно точны для глубокого недельного разбора.

3. Структурно видны две разные проблемы: многократные короткие входы в реактивную работу и крупные разрывы после тяжёлых блоков. Они вынесены в отдельные наблюдения, а не смешаны с топом времени.

4. Кандидаты на следующий фокус полезны как очередь решений, но не как автоматическая рекомендация. В реальном отчёте среди кандидатов оказалась уже завершённая встреча: Timeskein видит вложенное усилие, но пока не знает, закрыт ли смысловой результат.

5. Для выбора следующего периода отчёта хватило, чтобы принять три решения без ручной склейки дневников:

   - защитить продолжение свежего многоблочного трека по командным целям;
   - отдельно решить, продолжать или закрывать учебный трек, который получил заметное время, но давно не касался реальности;
   - считать снижение цены возврата после потери управляемости отдельной настройкой рабочего контура, а не ещё одним Work Item.

## Вердикт

- Произвольный диапазон: работает.
- Markdown: пригоден для чтения и передачи в LLM.
- JSON: сохраняет запрос, итоги, группировки, хронологию, события, captures, gaps, предупреждения и кандидатов.
- Предупреждения качества: дают полезный сигнал на реальных данных.
- Выбор 1–3 фокусов: возможен, но требует человеческого решения.
- P0 Period Report CLI: принят.
- Профили обзора: приняты для `weekly-review`, `sprint-review`, `track-retrospective` и `performance-evidence`; каждый явно сообщает свой вопрос и ограничения данных.
- Reflection Session: принят. В реальной базе сохранён недельный вывод и три решения: `protect-next-focus`, `reactive`, `park`.
- Повторное использование: `reflection:list` и повторный `report:period` показывают сохранённые решения.
- Track retrospective: принят. Реальный Track `Личные проекты / Timeskein` дал консервативный срез без поиска по названиям; два однозначных Work Item вошли в отчёт, смешанный Work Item остался Unclassified.
- Историческая честность: принята для новых данных. Старые блоки без снимков явно помечаются как восстановленные по текущему Work Item.

## Семантический proof

Проверенная команда:

```bash
pnpm report:period -- --from 2026-07-01 --to 2026-07-10 \
  --profile track-retrospective \
  --track Timeskein \
  --reflection-template /tmp/timeskein-track-reflection.json
```

Результат на реальной базе:

- Track `Личные проекты / Timeskein`;
- Label `dogfood`;
- 2 однозначно относящихся Work Item;
- 2 входа за два dogfood-дня, `10:49`;
- оба старых входа помечены `inferred-current`;
- 103 входа исходного периода без Track явно показаны как Unclassified и не приписаны Timeskein;
- сохранены решения `protect-next-focus` и `continue` с областью Track;
- повторный отчёт загрузил оба решения.

## Evidence story: состояние до gate

Migration 011 и новый отчётный слой добавили ручные типы `result`, `decision`, `blocker`, `next_step`, `observation`, Ref snapshots и явную проверку прежних решений. До записи новых реальных данных строгая команда честно не проходит:

```bash
pnpm evidence:gate -- --from 2026-07-10 --to 2026-07-11
```

Исходное состояние реальной базы:

- captured Timeskein-блоки: `0/3`;
- подтверждённые изменения: `0/1`;
- прежние `protect-next-focus` и `continue` видны как `no_evidence` candidates;
- Markdown уже содержит все шесть evidence-story разделов;
- резервная копия перед миграцией сохранена локально рядом с основной базой.

Это полезная отрицательная проверка: новый код не выдаёт старые 10:49 или текущие Work Item refs за доказанный результат.

## Evidence story: результат gate

После запуска новой сборки на той же реальной базе создан один явно размеченный Work Item `Timeskein: доказуемая история Track` с Track `Личные проекты / Timeskein` и Label `dogfood`.

Фактура:

- 3 новых фокус-блока, все с provenance `captured`;
- 4 typed evidence-записи: result, decision, observation, next_step;
- 1 подтверждённое изменение с историческим file-path Ref snapshot;
- 2 текущих Work Item refs показаны отдельно от 3 captured evidence snapshots;
- 7 других входов дня остались Unclassified и не попали в Timeskein-срез;
- запись evidence во всех трёх блоках не остановила и не переключила активный таймер;
- прежний `protect-next-focus` получил follow-up `fulfilled`;
- прежний `continue` получил follow-up `progressed`;
- обе проверки связаны с captured result event;
- повторный `reflection:list` показал решение и обе проверки.

Строгая команда прошла:

```text
captured Timeskein-блоки: 3/3
подтверждённые изменения: 1/1
typed evidence с captured-классификацией: 4/4
protect-next-focus: fulfilled
continue: progressed
```

Нативный macOS smoke отдельно подтвердил тот же Local API путь на упакованной `.app`: result + новый Ref сохраняются, активный Focus Session остаётся тем же.

## Что нужно дальше

Evidence-backed semantic-history gate закрыт. Варианты следующей цели:

- надёжно различать актуальный, завершённый, реактивный и припаркованный Track;
- улучшить длинные внутридневные заметки и этапы работы;
- перенести периодический обзор из CLI в приложение;
- добавить исторические снимки названий Work Item, если переименования начнут искажать старые отчёты.

Ведущий кандидат — минимальная Operational Reality: теперь Timeskein может доказать, что изменилось, но ещё не даёт столь же сильного ответа, какие долгие направления актуальны прямо сейчас и что с каждым делать дальше.

Автоматический сбор окон, URL и скриншотов для этого результата не потребовался.
