## Название

Ручной инвентарь работы (Manual-first Work Inventory / Manual-first ledger)

## Короткое описание

Timeskein даёт пользователю простой и быстрый "реестр текущих задач/проектов/вопросов" (Work Items), который поддерживается вручную: пользователь сам создаёт элементы работы, задаёт их состояние, фиксирует следующий шаг и хранит ссылки/якоря на контекст (refs).
Система ничего не "подглядывает" в фоне (нет наблюдения за активными окнами, вкладками, вводом, скриншотов и т.п.). `last_seen` обновляется только по явным действиям пользователя внутри Timeskein.

## Контекст и ценность

Проблема: при нескольких параллельных задачах контекст "размазывается" по разным системам (тикеты, чаты, документы, репозитории, заметки). После прерывания или переключения пользователь теряет:

* что именно сейчас актуально,
* в каком статусе это находится (делаю / жду / заблокировано / когда вернуться),
* что следующий шаг,
* где лежит контекст (ссылка/файл/тикет/чат).

Ценность MVP в постановке Manual-first:

* быстрый "снимок того, что на столе" без тяжёлой инфраструктуры,
* минимальные риски приватности,
* прочный фундамент для будущего автоматического контекста (когда появятся коллекторы/наблюдение) без ломки модели Work Items.

## User Story

Как пользователь, который ведёт несколько параллельных задач и постоянно прерывается,
я хочу иметь короткий список актуальных Work Items с состояниями, следующим шагом и ссылками на контекст,
чтобы за минуты восстанавливать контекст после паузы/переключения и понимать, что делать дальше.

## Основные понятия

### Work Item

Элемент работы (task/project/question), который пользователь хочет держать "в оперативной памяти".

Минимально Work Item содержит:

* `title` — краткое имя ("ABC-123: поправить валидацию", "Созвон с Петей про SLA"),
* `state` — состояние (`active`, `waiting`, `blocked`, `done`, `someday`, `unknown`),
* `note` — 1–3 строки: следующий шаг / что ждём / блокер / договорённость,
* `refs` — привязки к "миру": URL, ключ тикета, путь файла, ссылку на чат/тред, repo/issue и т.д.,
* `last_seen` — когда пользователь в последний раз явно "трогал" этот Work Item в Timeskein (touch/edit/open).

### Refs

Refs — это якоря для быстрого возвращения к контексту. В постановке Manual-first refs:

* добавляются вручную (paste/выбор файла/ручной ввод),
* нормализуются (чтобы не плодить дубликаты),
* не извлекаются автоматически из активного окна/вкладки (это отложено).

### "Актуальный" Work Item

В Manual-first MVP "актуальность" определяется так:

* `state` в `active|waiting|blocked` — всегда актуален,
* `pinned=true` — всегда актуален,
* либо пользователь недавно "трогал" item (через touch/edit/open), и он не `done` (это правило можно настроить позже; в MVP достаточно фиксированного окна, например 14 дней).

## Границы и принципиальные ограничения (важно)

Эта юзерстори реализуется без "онлайн-наблюдения" и потому сознательно НЕ решает:

* авто-обновление `last_seen` при посещении тех же вкладок/файлов,
* "создать Work Item из текущего контекста окна/вкладки" без ручного ввода refs,
* автоматическое предложение "похоже на ABC-123" на основе активного контекста,
* построение Episodes/Threads, восстановление "чем занимался в 14:37".

Зато решает то, что даёт базовую ценность даже при нулевом сборе сигналов: реестр актуальных дел + явные якоря + следующий шаг.

## Acceptance Criteria (критерии приёмки)

### 1) Просмотр инвентаря

* Есть команда/экран "Инвентарь", который показывает список Work Items.
* Для каждого Work Item видно: `title`, `state`, `last_seen` (в относительном виде), `note` (если есть), количество refs (или "есть/нет").
* Список отсортирован:

  1. pinned сверху,
  2. затем по порядку `active → blocked → waiting → unknown → someday → done`,
  3. затем по `last_seen` по убыванию (NULL/пустые — в конец).

### 2) Создание нового Work Item (вручную)

* Пользователь может создать Work Item, введя как минимум `title`.
* При создании можно (но не обязательно) сразу указать:

  * `state` (по умолчанию `active` или `unknown` — выбрать один и зафиксировать в реализации),
  * `note` (опционально),
  * один или несколько refs (опционально).
* Создание фиксируется в хранилище и переживает перезапуск агента.

### 3) Изменение состояния (state) быстрым действием

* Пользователь может за ≤2 действий поменять `state` Work Item на одно из:
  `active`, `waiting`, `blocked`, `done`, `someday`, `unknown`.
* Изменение:

  * сохраняется,
  * обновляет `updated_at`,
  * обновляет `last_seen` (как "я явно работал с этим item"),
  * (желательно) пишет событие в `work_item_events`.

### 4) Редактирование заметки (note)

* Пользователь может быстро добавить/изменить `note` (короткий "next step / что ждём / блокер").
* Изменение:

  * сохраняется,
  * обновляет `updated_at`,
  * обновляет `last_seen`.

### 5) "Touch" (явно отметить, что я снова вернулся к задаче)

* Есть действие "Touch" (или эквивалент), которое:

  * обновляет `last_seen` текущего Work Item на "сейчас",
  * не меняет `state` и `note`.
* Touch доступен:

  * из списка инвентаря (на выбранном элементе),
  * и/или из карточки Work Item.

Зачем: это заменяет автоматический `last_seen` из будущих коллекторов, но остаётся быстрым и честным механизмом.

### 6) Pin/Unpin

* Пользователь может закрепить (pin) Work Item.
* Pin влияет на сортировку (закреплённые всегда сверху).
* Pin/Unpin сохраняется и обновляет `updated_at` + `last_seen`.

### 7) Управление refs (привязками)

* Пользователь может:

  * добавить ref к существующему Work Item,
  * удалить ref у Work Item.
* Типы refs в MVP можно принять минимально:

  * URL,
  * file path,
  * "custom" (произвольная строка).
    (Поддержка "issue_key" типа `ABC-123` можно сделать как частный случай custom или отдельный kind — на усмотрение реализации.)
* При добавлении ref выполняется нормализация (хотя бы трим/канонизация URL без сложных правил).
* При добавлении ref система проверяет дубликаты:

  * если такой ref уже привязан к этому Work Item — не добавлять второй раз,
  * если ref уже привязан к другому Work Item — показать явное предупреждение и дать выбор:

    * "всё равно добавить",
    * "открыть существующий Work Item с этим ref".
      (Это важный механизм "не плодить мусор" в manual-first режиме.)

### 8) Открытие контекста (Open last ref / Open ref)

* Пользователь может из инвентаря открыть:

  * "последний ref" (если refs несколько),
  * или выбрать ref из списка (если UI позволяет).
* Открытие ref:

  * не должно требовать сети (кроме тех refs, которые сами сетевые URL),
  * должно обновлять `last_seen` Work Item (потому что пользователь явно вернулся к контексту через Timeskein).

### 9) Оффлайн и локальность

* Вся фича работает без сети (создание/редактирование/просмотр/сортировка).
* Хранилище локальное (например, SQLite как в архитектурных документах).
* Утечки "контекста" наружу отсутствуют по умолчанию (никакой отправки данных в облако).

### 10) Приватность в постановке Manual-first

Поскольку нет фонового сбора контекста, приватность в MVP упрощена, но базовые предохранители должны быть:

* Никаких скриншотов/аудио/текстов страниц.
* Refs добавляются только явным действием пользователя.
* При необходимости есть настройка "denylist доменов" для URL refs:

  * если пользователь пытается добавить ref на домен из denylist, система либо:

    * запрещает сохранение,
    * либо сохраняет в отредактированном виде (например, только `domain:<host>` вместо полного URL).
      Выбрать один вариант политики и закрепить.

## Примеры взаимодействия с системой (настоящая история пользователя)

Ниже — пример как это ощущается пользователем. Формат условный (CLI/палитра команд), UI не фиксируем — важны действия и данные.

### История: "Вернуться в задачу после прерывания"

Утро. Пользователь начал разбирать баг в тикете `ABC-123`, но его отвлекли на срочный созвон.
Через 3 часа он возвращается и понимает: "а что я делал, где остановился, что следующий шаг?"

1. Ещё когда он начинал, он за 30 секунд занёс задачу в Timeskein:

* Команда: `timeskein add`
* Timeskein спрашивает поля (или открывает форму):

  * Title: `ABC-123: Ошибка валидации при импорте`
  * State: `active`
  * Note: `Проверить кейс с пустым phone; добавить тест; посмотреть где падает`
  * Ref: `https://jira.company.local/browse/ABC-123`

Timeskein сохраняет Work Item.

2. Созвон прерывает работу. Спустя 3 часа пользователь открывает инвентарь:

* Команда: `timeskein inventory`
* Timeskein показывает (условно):

  * `active`  ABC-123: Ошибка валидации при импорте   last_seen: 3h ago   note: Проверить кейс с пустым phone...
  * `waiting` Ответ от дизайнера по API              last_seen: 2d ago   note: жду ревью до пятницы
  * `blocked` Доступ к staging                       last_seen: 5d ago   note: жду прав на Vault

3. Пользователь выбирает `ABC-123` и делает "Open last ref":

* Timeskein открывает браузер на URL тикета.
* Одновременно обновляет `last_seen` у Work Item (потому что пользователь вернулся к нему через систему).

4. Пользователь читает тикет и понимает, что следующий шаг изменился (нужно уточнить контракт):

* Команда: `timeskein note ABC-123`
* Новая заметка: `Согласовать: пустой phone = null или ""? Написать Пете; затем поправить валидатор`

5. После того, как он написал Пете, он ставит задачу в ожидание:

* Команда/действие: `set state → waiting`
* Note уже содержит, чего ждём.
* Инвентарь теперь сразу отражает реальность: "я не делаю прямо сейчас, я жду".

Смысл: даже без автоматического наблюдения пользователь за минуты восстановил контекст, не разыскивая "где оно было" по памяти и вкладкам.

## Примеры сценариев (Gherkin)

### Сценарий 1: Посмотреть, что сейчас актуально

* Given у пользователя есть несколько Work Items с разными состояниями и pinned
* When пользователь открывает "Инвентарь"
* Then он видит список, отсортированный по pinned → state → last_seen
* And по каждому элементу видно состояние и короткую заметку

### Сценарий 2: Создать задачу и сразу зафиксировать следующий шаг

* Given пользователь хочет начать новую задачу
* When он создаёт Work Item с title и note
* Then Work Item появляется в инвентаре со state по умолчанию
* And last_seen установлен на текущее время

### Сценарий 3: Добавить ref и не создать дубликат

* Given существует Work Item A с ref `https://example.com/x`
* When пользователь пытается добавить тот же ref в Work Item A
* Then система не добавляет второй раз тот же ref
* And (опционально) сообщает, что ref уже существует

### Сценарий 4: Предупредить о ref, который уже привязан к другому Work Item

* Given существует Work Item A с ref `ABC-123`
* When пользователь добавляет ref `ABC-123` в Work Item B
* Then система предупреждает, что ref уже связан с Work Item A
* And предлагает открыть A или всё равно продолжить

## Out of Scope (для этой юзерстори)

Следующее откладывается до появления системы онлайн-наблюдения/коллекторов или до отдельной истории про интеграции "из текущего контекста":

* Автоматический `last_seen` по посещениям окон/вкладок/файлов.
* Команда "создать/привязать из текущего контекста" с авто‑извлечением URL/заголовка.
* Подсказки "похоже на …" на основе текущего активного контекста.
* ContextEvent log как поток фоновых событий (active window, browser context, idle).
* Episodes/Threads, семантический поиск по содержимому, "что я делал в момент X".
* Кросс-девайс синхронизация.
* Скриншоты/аудио/полные тексты страниц.

## Приложение A: Технические наброски для дизайна реализации (Draft)

Этот раздел не является частью критериев приёмки, но фиксирует реализационный "скелет", чтобы дизайн не пришлось собирать заново.

### A1. Минимальный слой данных (SQLite)

Использовать схему, совместимую с RFC-0001, но без обязательного `context_events` на первом шаге.

**Таблица `work_items`**

* `id` TEXT (ULID/UUID)
* `title` TEXT NOT NULL
* `type` TEXT NULL (`task|project|question` — опционально)
* `state` TEXT NOT NULL (`active|waiting|blocked|done|someday|unknown`)
* `pinned` INTEGER NOT NULL DEFAULT 0
* `note` TEXT NULL
* `created_at` DATETIME NOT NULL
* `updated_at` DATETIME NOT NULL
* `last_seen_at` DATETIME NULL
  В Manual-first: это "last_touched_at", обновляется только действиями пользователя (touch/edit/open/state/note/ref change).
* `deleted_at` DATETIME NULL (soft delete — опционально)

**Таблица `refs`**

* `id` TEXT
* `kind` TEXT (`url|file_path|custom` … расширяемо)
* `value` TEXT (нормализованное значение)
* `created_at` DATETIME

**Таблица `work_item_refs`**

* `work_item_id` TEXT
* `ref_id` TEXT
* `created_at` DATETIME
* (опционально) `is_primary` INTEGER DEFAULT 0
  чтобы понимать "last ref"/"главный ref" без сложной логики.

**Таблица `work_item_events` (append-only, желательно с первого дня)**

* `id` TEXT
* `ts` DATETIME
* `work_item_id` TEXT
* `kind` TEXT (`created|touched|state_changed|note_changed|pinned|unpinned|ref_attached|ref_removed|opened_ref|deleted`)
* `payload` JSON/TEXT

Зачем события уже в Manual-first:

* аудит изменений,
* восстановление "что я делал внутри Timeskein",
* фундамент для будущего event-sourcing.

### A2. Нормализация refs (минимальный алгоритм)

**URL**

* trim пробелов,
* привести схему/хост к нижнему регистру,
* убрать якорь `#...` (опционально, зависит от ценности),
* (опционально) убрать tracking параметры (utm_*) — можно позже.

**file path**

* trim,
* нормализовать разделители (`\`/`/`) под текущую OS,
* хранить как есть + отдельное поле "os" можно позже.

**custom**

* trim,
* запретить пустые строки.

### A3. Вычисление представления "Инвентарь"

`list_inventory(now)`:

* брать `work_items` где `deleted_at IS NULL`
* (опционально) скрывать `done`, если не pinned и last_seen слишком старый
* сортировать:

  1. pinned desc
  2. state_rank asc (active=1, blocked=2, waiting=3, unknown=4, someday=5, done=6)
  3. last_seen_at desc NULLS LAST

### A4. Команды/use-cases (UI-агностично)

Минимальные use-cases (внутренние интерфейсы), которые покроют историю:

* `list_inventory() -> WorkItemView[]`
* `create_work_item(title, state?, note?, refs[]) -> work_item_id`
* `touch_work_item(work_item_id)`
* `set_state(work_item_id, state)`
* `set_note(work_item_id, note)`
* `toggle_pin(work_item_id)`
* `add_ref(work_item_id, ref_kind, ref_value)`
* `remove_ref(work_item_id, ref_id)`
* `open_ref(work_item_id, ref_id? | last_primary)`

Везде, где есть действие пользователя:

* обновлять `work_items.updated_at`,
* обновлять `work_items.last_seen_at`,
* писать `work_item_events`.

### A5. Механизм дедупликации refs

При `add_ref`:

* найти `refs` по (`kind`, `value`) после нормализации;
* если нет — создать ref;
* если ref уже привязан к этому Work Item — no-op;
* если ref привязан к другому Work Item:

  * вернуть предупреждение "ref уже использован" + список кандидатов (work_item_id, title, state),
  * UI решает: открыть существующий / продолжить.

### A6. Политика "denylist доменов" (минимальная)

Конфиг в локальном файле (например `~/.timeskein/config.json` или внутри БД):

* `deny_domains: ["mail.google.com", "bank.example.com"]`
* `deny_policy: "block" | "redact_to_domain"`

Поведение:

* если `kind=url` и домен в denylist:

  * `block`: отклонить добавление с понятным сообщением,
  * `redact_to_domain`: вместо полного URL сохранять `kind=custom`, `value="domain:mail.google.com"` (или `kind=domain` если решим ввести).

### A7. Миграционный путь к будущему "наблюдению"

Когда появятся collectors/online-наблюдение:

* добавляется `context_events` log (как в ADR/RFC),
* появляется автоматический `last_seen_at` от посещений refs,
* появится команда "capture current context" и подсказки (вариант B),
* при этом manual-first механика остаётся базовой: state и note — источник истины пользователя, автомат не переписывает их без явного действия.

## Приложение B: Путь к расширению без поломки доверия

Этот раздел описывает, как Manual-first механика становится фундаментом для будущей автоматизации.

### B1. Manual-first как неизменный фундамент

Manual-first режим (Level 0) остаётся базовым на всех уровнях зрелости системы:

| Принцип | Гарантия |
|---------|----------|
| `state` и `note` — источник истины пользователя | Автоматика никогда не перезаписывает их без явного действия |
| Ручной режим работает без разрешений | Даже при включённых collectors базовая функциональность не требует accessibility/screen capture |
| Данные объяснимы | Каждый автоматически добавленный ref/событие имеет provenance (откуда взялось) |

### B2. Level 2: Semantics-first connectors

При появлении connectors (явный захват контекста):

**Новые возможности:**

* Команда "Захватить текущий контекст" — извлечь refs из активного окна/вкладки по явному действию пользователя
* Авто-извлечение refs из URL/заголовка (по команде, не фоном)
* Подсказки по сильным refs ("Похоже на ABC-123, открыть?")
* `last_seen` может обновляться по явно привязанным refs

**Что НЕ меняется:**

* Work Items создаются только по подтверждению пользователя
* `state` и `note` не перезаписываются автоматикой
* Ручной режим работает без connectors

**Зависимости:**

* [RFC-0005: Event Ingest + SourceNode + Pairing](../rfc/0005-event-ingest-source-nodes.md)
* [User Story: Захват текущего контекста](01_user_story_context_capture.md)

### B3. Level 3: Full context collectors

При появлении always-on collectors (фоновое наблюдение):

**Новые возможности:**

* Фоновый сбор ContextEvents (активное окно, URL вкладки, idle)
* Автоматическое обновление `last_seen` по посещениям refs
* Построение Episodes (интервалы с единым контекстом)
* Построение Threads (сквозные темы)
* Артефакты (скриншоты, транскрипты) с TTL

**Что НЕ меняется:**

* `state` и `note` остаются источником истины пользователя
* Пользователь включает каждый collector явно
* Каждый источник требует pairing (одобрения)
* При отзыве доверия можно удалить все данные от источника

**Зависимости:**

* [RFC-0005: Event Ingest + SourceNode + Pairing](../rfc/0005-event-ingest-source-nodes.md)
* [RFC-0006: Retention/TTL + Distillation](../rfc/0006-retention-ttl-distillation.md)

### B4. Ключевые термины для будущего

**SourceNode** — источник событий (collector, connector, extension). Объявляет манифест с capabilities и permissions. Требует явного одобрения (pairing) перед началом работы.

**Provenance** — происхождение данных. Каждое автоматически добавленное событие/ref знает:
* `source_id` — какой источник создал данные
* `timestamp` — когда
* `policies_applied` — какие правила были применены

Провенанс позволяет удалить все данные от конкретного источника при отзыве доверия.

**Distillation** — процесс превращения сырых событий и артефактов в Episodes/Threads перед удалением по TTL. Принцип "Distill before forget" гарантирует, что ценность извлекается до удаления сырых данных.

См. [Глоссарий](../glossary.md) для полного списка терминов.
