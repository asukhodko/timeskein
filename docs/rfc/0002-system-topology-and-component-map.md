# RFC 0002: Топология системы и карта компонентов (multi-device)

## Зачем этот документ

Мы переходим от user-story и UX к проектированию независимых частей системы. Этот документ фиксирует:

* где в Timeskein “бэкенды”, а где “приложения-поверхности” (UI),
* сколько условно независимых кусков нужно,
* как эти куски связаны,
* как это масштабируется на несколько устройств пользователя (Windows, macOS, Android),
* как этот расклад готовит почву для будущего полного сбора контекста на всех устройствах.

Это не заменяет ADR-0001. Это “deployment view + component map”, чтобы дальше писать отдельные RFC/дизайн-доки на каждый компонент.

---

## Scope

В рамках этого документа:

* описываем разделение на независимые единицы (process/package/service),
* определяем интерфейсы и направления зависимостей,
* выделяем контуры: manual-first inventory (user-story-02), sync (multi-device), collectors (полный контекст).

---

## Non-goals

* не выбираем конкретный стек (Rust/Go/TS, Tauri/Electron, Protobuf/JSON),
* не проектируем внутренние таблицы БД подробно (это в отдельных RFC),
* не обсуждаем UI/UX детали (они в mvp UX документе),
* не решаем вопросы ML/семантики (это позже).

---

## Термины (чтобы не путаться)

### Surface

Пользовательский интерфейс (палитра/трей/экран в мобильном приложении). Surface не хранит “истину” сам по себе, он вызывает локальный бэкенд.

### Device Agent (локальный бэкенд)

Фоновый процесс/служба на каждом устройстве пользователя. Единая точка правды на устройстве: хранит данные, выполняет юзкейсы, принимает события от коллекторов и синхронизируется с Hub.

### Hub Backend (центральный бэкенд)

Сервер, который объединяет данные пользователя от всех устройств и обеспечивает синхронизацию.

### Collector

Платформенно-специфичный сборщик “следов активности” (позже). Коллектор производит события и отправляет их в Device Agent. Коллектор не должен напрямую писать в БД или напрямую взаимодействовать с UI.

### Connector / Extension

Интеграция с конкретным приложением/сервисом (например, расширение браузера, интеграция мессенджера). По смыслу это тоже источник событий (как коллектор), но более “семантический”.

---

## Высокоуровневая топология (как это выглядит у пользователя)

У пользователя несколько устройств (Windows, macOS, Android). На каждом устройстве должен существовать локальный агент. В идеале Surface и Agent могут поставляться одним инсталлятором, но архитектурно остаются разными ролями.

### Deployment-схема

```
Windows:  [Desktop Surface]  <—local IPC—>  [Device Agent]  <—HTTPS sync—>  [Hub Backend]
macOS:    [Desktop Surface]  <—local IPC—>  [Device Agent]  <—HTTPS sync—>  [Hub Backend]
Android:  [Android App UI + embedded Agent] <—HTTPS sync—>  [Hub Backend]

Future: collectors/events
Windows:  [Collectors Pack] —> [Device Agent]
macOS:    [Collectors Pack] —> [Device Agent]
Android:  [Collectors Pack] —> [Device Agent] (внутри приложения/сервиса)
```

Ключевые принципы:

* Surface всегда общается с локальным Agent (а не напрямую с Hub).
* Collectors всегда общаются с локальным Agent (а не с UI).
* Hub нужен для “склейки” устройств и общего индекса (позже).

## Сколько независимых кусков будет

Ниже — список независимых компонентов (unit’ов), которые можно проектировать и реализовывать относительно автономно.

Для удобства каждому компоненту дан идентификатор.

### TS-AGENT: Timeskein Device Agent (локальный бэкенд)

Что это: единая точка правды на устройстве. Один агент на устройство.

Отвечает за:

* выполнение всех юзкейсов manual-first inventory (user-story-02),
* локальное хранение (SQLite/эквивалент),
* локальные настройки (hotkey, denylist, политики),
* локальный event log (опционально, но желательно),
* локальный API для Surface (IPC/RPC/localhost),
* при наличии: приём событий от Collectors/Connectors,
* при наличии: sync с Hub.

Архитектурное направление:

* core-first / ports & adapters: домен и юзкейсы в центре, инфраструктура снаружи,
* детерминируемое время (Clock port), транзакционность юзкейсов,
* одинаковая модель на всех платформах; OS-специфика только в адаптерах.

Интерфейсы:

* inbound: Local API (commands/queries) от Surface, Event Ingest API от Collectors
* outbound: Storage, OS services (opener), Sync client

---

### TS-DESKTOP: Desktop Surfaces (Windows/macOS)

Что это: пользовательские поверхности на десктопе. Можно как один desktop app, внутри которого несколько UI режимов.

Состав:

* command palette overlay (основной UI),
* tray/menubar (вторичный вход),
* (опционально) full management UI (редкий экран).

Отвечает за:

* UX-потоки из UI/UX документа для user-story-02,
* отображение инвентаря, поиск, быстрые действия,
* диалоги refs (добавление/конфликт/выбор/open),
* показ ошибок и статусов.

Архитектурное направление:

* Surface тонкий: никакой бизнес-логики и правил refs/denylist в UI,
* общение только с локальным Agent через Local API,
* можно реализовывать отдельно от Agent как отдельный процесс (прочнее), но допускается “монолит в одном бинаре” на старте при сохранении границ модулей.

---

### TS-ANDROID: Android App Surface (Android)

Что это: мобильное приложение пользователя.

Роли:

* Surface: просмотр/быстрые действия с inventory,
* контейнер: внутри приложения живёт embedded Agent (или отдельный сервис) + локальное хранилище,
* точка для Android-коллекторов (в будущем).

Отвечает за:

* quick interactions (touch/state/note/add ref/open ref),
* удобный импорт ref через Android share sheet,
* offline-first работу.

Архитектурное направление:

* “маленький Surface”: мобильный интерфейс не обязан быть супер-мощным, но должен быть быстрым,
* embedded Agent использует тот же домен/юзкейсы/модель данных, что и desktop.

---

### TS-HUB: Hub Backend (центральный бэкенд)

Что это: серверный хаб синхронизации и объединения устройств пользователя.

Отвечает за:

* регистрацию пользователя/устройств,
* приём данных/изменений от устройств,
* отдачу изменений на устройства,
* хранение общей копии данных пользователя,
* (позже) глобальный индекс/поиск/агрегации таймлайна.

Архитектурное направление:

* начинать как “sync hub”, без умной семантики,
* проектировать под оффлайн и буферизацию (устройства могут присылать пачки задним числом),
* безопасность: device identity, авторизация, шифрование в транспортном уровне, возможность self-host.

---

### TS-SYNC: Sync Engine (клиент синхронизации, модуль в Agent)

Что это: подсистема в TS-AGENT, которая обеспечивает репликацию данных с TS-HUB.

Отвечает за:

* outbox изменений (что надо отправить),
* inbox изменений (что применить),
* простую стратегию конфликтов (минимально достаточно),
* ретраи/backoff/устойчивость к оффлайну,
* идемпотентность (повторная доставка не ломает данные).

Архитектурное направление:

* предпочтительно реплицировать события/патчи, а не “перезаливать весь стейт”,
* эволюционно расширяется на новые типы событий (context events, episodes и т.п.).

---

### TS-SCHEMA: Shared Data Model & Protocol (общая контрактная библиотека)

Что это: общий пакет (library), который определяет:

* DTO/события для Local API и Sync API,
* версионирование схемы,
* сериализацию/десериализацию,
* совместимость версий (backward/forward).

Отвечает за:

* единое понимание данных между desktop, android, hub,
* минимизацию “расхождения смыслов” и миграционных проблем.

Архитектурное направление:

* один источник правды для контрактов,
* строгая дисциплина версий (schema_version + migration policy).

---

### TS-COLLECTORS-WIN / TS-COLLECTORS-MAC / TS-COLLECTORS-ANDROID: Collector Packs (будущий контур)

Что это: набор коллекторов активности, специфичный для платформы.

Отвечает за:

* сбор сигналов активности (в рамках разрешений и политики приватности),
* преобразование в канонические события (например `ContextEvent`),
* доставку событий в TS-AGENT (event ingest),
* возможность отключения/denylist/провенанс.

Архитектурное направление:

* коллекторы не пишут в БД напрямую,
* коллекторы можно включать/выключать независимо,
* “local-first обработка”: максимум очистки/редакции на устройстве.

Важно: этот контур критичен для цели “учесть всю активность на всех устройствах”, но он не обязателен для запуска user-story-02. Он должен быть спроектирован так, чтобы добавляться позже без поломки manual-first основы.

---

### TS-CONNECTORS: Connectors / Extensions (опционально, но очень эффективно)

Что это: интеграции с конкретными приложениями/сервисами (браузер extension, Obsidian plugin, мессенджеры и т.п.)

Отвечает за:

* более точные “семантические” события, чем универсальные коллекторы,
* быстрый “Send to Timeskein” (явный action пользователя),
* передачу структурированного контекста (ID треда, URL, выделение — если разрешено).

Архитектурное направление:

* работают как источники событий и общаются только с TS-AGENT,
* scopes и permissions минимальные,
* все чувствительные решения (редакция, denylist) на стороне агента либо на стороне коннектора (дублируемо).

---

## Как они связаны (граф зависимостей)

Упрощённая схема зависимостей по направлению:

* Surfaces (desktop/android UI) → Local API → TS-AGENT
* Collectors/Connectors → Event Ingest API → TS-AGENT
* TS-AGENT → Storage (локально)
* TS-AGENT → TS-SYNC → TS-HUB
* TS-SCHEMA используется всеми (agent/surfaces/hub/sync)

Ключевой принцип: TS-AGENT — центральная точка на устройстве. Она изолирует:

* UI от сложности хранения и синхронизации,
* collectors от бизнес-правил,
* hub от платформенной специфики.

## Потоки данных (чтобы было понятно “что куда течёт”)

### Поток A: Manual-first inventory (user-story-02) на одном устройстве

1. Пользователь вызывает палитру (TS-DESKTOP)
2. Выбирает действие (add/touch/state/note/ref/open)
3. TS-DESKTOP вызывает Local API TS-AGENT
4. TS-AGENT:

   * валидирует,
   * нормализует refs,
   * пишет в БД,
   * обновляет last_seen,
   * (опционально) пишет work_item_event
5. TS-DESKTOP получает обновлённый view и отображает

Никакой фоновой активности тут нет.

---

### Поток B: Multi-device (Win + Mac + Android)

1. На Windows пользователь обновляет note у WorkItem
2. TS-AGENT (Windows) пишет изменение локально и кладёт запись в outbox TS-SYNC
3. TS-SYNC отправляет изменение в TS-HUB
4. TS-HUB сохраняет и делает доступным для других устройств
5. TS-SYNC на Android подтягивает изменения
6. TS-AGENT (Android) применяет изменения локально
7. Android UI показывает обновлённый инвентарь

---

### Поток C: Полный сбор контекста на всех устройствах (будущее)

1. TS-COLLECTORS-<platform> получает сигнал (например “смена активности/приложения/страницы”)
2. Коллектор превращает сигнал в `ContextEvent` и отправляет в Event Ingest API TS-AGENT
3. TS-AGENT:

   * применяет denylist/policies,
   * сохраняет событие,
   * (позже) строит Episodes/Threads,
   * (позже) синхронизирует события с Hub

Важно: collectors добавляют “богатство контекста” поверх manual-first основы, но не ломают Work Items как источник пользовательской истины (state/note/pin).

---

## Минимальный набор для запуска user-story-02

Чтобы user-story-02 работала на одном десктопе:

* TS-AGENT
* TS-DESKTOP
* локальное хранилище (внутри TS-AGENT)
* минимум OS adapters (hotkey, opener, clipboard по явной команде)

Чтобы user-story-02 работала на всех устройствах пользователя (Win + Mac + Android):

* всё выше
* TS-HUB
* TS-SYNC (в агентах)
* TS-ANDROID
* TS-SCHEMA (контракты)

Collectors/Connectors не обязательны для user-story-02, но обязательны для будущей цели “полный сбор контекста”.

## Итог

Мы фиксируем, что Timeskein — это:

* на устройстве: TS-AGENT (локальный бэкенд) + Surfaces (UI),
* между устройствами: TS-SYNC + TS-HUB,
* для будущего полного контекста: TS-COLLECTORS + TS-CONNECTORS, которые питают события в TS-AGENT.
