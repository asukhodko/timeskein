# RFC-0009: Causal Work Memory and Operational Reality

## Статус

**Accepted Operational Reality v1 (2026-07-16); Working Memory Bridge
implemented, acceptance pending (2026-07-22).** Двухдневный gate причинного
стержня и Operational Reality пройден. Следующий ручной слой реализован, но не
принимается до реального 1/3/7-дневного возврата. К 28 июля в выбранном деле
сохранены четыре записи, Track и одиннадцать дневных снимков результата, но
мягкий gate ещё не видит полного baseline D0: перед новым проверочным блоком
нужны смысловая запись, материал и активный этап.

## Цель

Определить общий стержень Timeskein, на который смогут опираться ручной дневной
контур, Operational Reality, периодические обзоры, SourceNodes, синхронизация и
ИИ-анализ.

Целевой вопрос системы:

> Что было важно, что происходило, что изменилось, чем это подтверждается,
> какое решение принято и что теперь следует делать?

## Причинная цепочка

```text
намерение -> эпизод работы -> контекст -> действие -> изменение
           -> доказательство -> решение -> следующий шаг
```

Цепочка не требует, чтобы каждое звено было заполнено. Пропуск должен быть
видимым как неизвестность, а не достраиваться по длительности или названию.

## Соответствие текущей модели

| Причинная роль | Текущая сущность | Дальнее расширение |
| --- | --- | --- |
| Намерение и обязательство | Work Item, Track, Dispatch Event | подтверждённый active set и обязательства периода |
| Эпизод работы | Focus Session | Episode из ручных и наблюдаемых событий |
| Контекст | Ref, Capture, Day/Work Item Event | ContextEvent и SourceNode observation |
| Изменение | typed `result` event | проверяемый state transition или outcome claim |
| Доказательство | Evidence Ref Snapshot | дистиллированный артефакт с provenance |
| Решение | Reflection Decision | решение с областью действия и сроком проверки |
| Следующий шаг | `next_step`, note | подтверждённый next action с состоянием проверки |

Track остаётся заданным пользователем долгим направлением. Thread в будущем
может быть вычисленной связью между эпизодами; эти понятия не объединяются.

## Слои данных

### Canonical

Долгоживущие факты и пользовательские решения:

- Work Items, Tracks, Labels и их исторические изменения;
- Focus Sessions и ручные события;
- наблюдения SourceNodes с provenance; их содержимое остаётся недоверенным;
- Reflection Sessions, решения, исправления и подтверждения;
- refs и дистиллированные факты, выбранные для долговременного хранения.

### Derived

Пересчитываемые представления:

- Operational Reality;
- Context Packs для возврата, обзора и внешнего анализа;
- Episodes и Threads;
- отчёты, кандидаты следующего фокуса и паттерны;
- embeddings, индексы и LLM-интерпретации.

### Ephemeral

Чувствительные или тяжёлые исходники с TTL:

- screen chunks и временные кадры;
- сырой текст внешнего источника, если он не нужен долговременно;
- промежуточные данные OCR и обработки.

### Control

Разрешения и управление:

- SourceNode pairing, pause, health и revocation;
- sensitivity, redaction и PolicyGate;
- TTL, storage budget, purge и audit;
- настройки провайдера и граница локальной/внешней обработки.

## Общий provenance

Новые наблюдения и интерпретации должны поддерживать минимальный envelope:

```text
source_id
device_id
observed_at
recorded_at
schema_version
sensitivity
content_trust
temporal_precision
confidence
correlation_id
derivation_version
provider_id
model_id
prompt_version
processing_location
```

Не каждое поле обязательно для ручного Level 0 события. Отсутствующее значение
не подменяется фиктивным. Для машинного вывода обязательны входные записи,
источник, версия преобразования, место обработки и доступные сведения о модели.
Любой внешний текст и OCR получают `content_trust: untrusted` и никогда не
становятся инструкцией агенту.

## Artifact, Observation, Derivation и Context Pack

Будущий автоматический контекст не вводит параллельную память. Он использует
общий путь:

```text
Artifact -> Observation -> Derivation -> Accepted Claim
                         -> Context Pack projection
```

Artifact хранит материал или указатель на него. Observation сообщает только о
наблюдении. Derivation является пересчитываемой интерпретацией. Только явно
принятый пользователем claim может стать причинной записью состояния,
результата, решения или следующего действия.

`Context Pack` является переносимой проекцией для возврата в дело, обзора или
ИИ-анализа. UI, Markdown, JSON, Codex, другая модель и будущий MCP-сервер читают
один смысловой пакет, не меняя каноническую модель под конкретного потребителя.
Полный контракт определён в [RFC-0010](0010-artifacts-observations-and-context-packs.md).

### Реализация Working Memory Bridge

Миграция `014_working_memory_bridge.sql` добавляет хронологические записи и
редакции рабочей памяти, этапы Work Item, исторические снимки этапа и дневного
результата Focus Session, устойчивые aliases после объединения дублей и явное
переполнение договора дня. Существующий журнал импортируется как
`legacy_current`, а новые записи сохраняют происхождение и семантический снимок.

Поверхность `Рабочая память` показывает последнее подтверждённое изменение,
текущий этап, вопросы, материалы и следующий шаг. Остановка фокуса может одним
действием сохранить `результат -> изменение состояния -> следующий физический
шаг`. Профили `work-item-reentry` и `track-reentry` строятся из канонических
данных как одна детерминированная проекция для UI, Markdown и JSON.
`as_of` ограничивает не только время событий, но и доступные к этому моменту
редакции памяти и переходы этапов: поздняя правка или tombstone не меняет
раннюю проекцию. При объединении дублей конфликт двух разных текущих Track не
разрешается молча: пользователь сначала выбирает общее направление.

Автоматические проверки доказывают миграции, историю редакций и удалений,
снимки, merge/alias, API/mock parity и воспроизводимость Context Pack. Они не
доказывают снижение цены реального возврата: этот вывод разрешён только после
протокола из [dogfood Working Memory](../dogfood-working-memory.md).

## Operational Reality

Operational Reality является текущей проекцией причинной памяти, а не новым
списком задач.

### Что попадает в проекцию

- открытые Work Items и Tracks;
- решения обзоров, ожидающие проверки;
- captures и meeting tails без исхода;
- blocked/waiting обязательства;
- давно не тронутые, но явно важные направления;
- высокая активность без зафиксированного изменения;
- защищённые фокусы, не получившие следующего входа.

Полная проекция и очередь внимания различаются. Обычный legacy Work Item с
неизвестным состоянием или отсутствующим следующим шагом остаётся в `Показать
всё`, но не становится запросом решения без дополнительного сигнала. В очередь
v1 попадают явные состояния внимания, незавершённые решения обзоров, открытые
следующие действия, captures, закреплённые пункты без шага и не менее двух
учтённых часов без записанного результата. Порог консервативен и должен
уточняться по dogfood, а не выдаваться за оценку ценности работы.

### Состояния первого среза

`active`, `waiting`, `blocked`, `parked`, `reactive`, `completed`,
`stale-important`, `meeting-tail`, `unknown`.

### Карточка реальности

Каждый пункт показывает:

- состояние и его provenance;
- почему пункт сейчас виден;
- последнее подтверждённое касание;
- факты и evidence;
- уверенность вывода;
- следующий шаг и статус его проверки;
- ручные действия: подтвердить, исправить, закрыть, ждать, заблокировать,
  припарковать или признать неактуальным.

Система не выводит результат из длительности. Машинное состояние не заменяет
ручное без подтверждения.

### Реализация v1

- миграция `012_causal_work_spine.sql` хранит append-only причинные записи;
- типы записи: intent, state assertion, result, decision, next action,
  confirmation и correction;
- correction содержит `supersedes_id`, исходная запись сохраняется;
- причинная запись фиксирует `occurred_at` и `recorded_at`, source, provenance,
  confidence, schema/device/correlation и семантический snapshot;
- `operational_reality.list` строит детерминированную проекцию на `as_of`;
- React-панель показывает основания и неизвестности, принимает исправление,
  показывает captured Ref snapshots, управляет next action, Reflection
  follow-up, исключением неактуального пункта и стартом дела;
- карточка Track показывает недавние результаты и решения связанных Work Item
  по сохранённому историческому пути, включая evidence Refs; последующая
  переклассификация Work Item не меняет это основание;
- JSON доступен через Local API и `pnpm export:operational-reality`;
- superseded-записи остаются в causal history, но перестают влиять на текущую
  проекцию; переклассификация и удаление typed evidence оставляют correction;
- существующие дневные и периодические отчёты продолжают читать свои
  исторические снимки и не меняются от поздней коррекции текущего состояния.

Legacy typed evidence и Reflection decisions читаются через адаптеры и
материализуются в causal history без двойного показа. Полный event sourcing не
используется.

### Приёмка v1

15–16 июля Operational Reality использовалась на реальной работе как точка
выбора и возврата. Строгий gate подтвердил два дня, 11 стартов из проекции,
состояния `meeting-tail`, `stale-important`, `waiting`, `reactive`, устойчивую
коррекцию после перезапуска, три Reflection follow-up и причинную цепочку
`intent -> result с Ref -> next action`.

Приёмка показала две важные границы модели:

- диспетчеризация должна выбирать небольшой договор дня из Operational Reality,
  а не конкурировать с ней как второй свободный список;
- договор дня не определяет Operational Reality и не является обязательным
  условием доступа к ней. Operational Reality остаётся полной производной
  проекцией, а Рабочий контур является пользовательским срезом поверх неё;
- причинная память не может считаться надёжной поверх противоречивой временной
  шкалы. API теперь не допускает новых пересечений фокус-блоков, а дневной и
  периодический отчёты явно блокируют или предупреждают о старых пересечениях.

События старше текущего дня в основаниях показываются с датой. `Enter` открывает
редактор Work Item даже при наличии URL; ссылки остаются отдельным действием.
Это устраняет два дефекта, мешавших проверять старые основания и обслуживать
реальные пункты проекции.

День 27 июля выявил регрессию смысла после объединения интерфейса: название
`Рабочий контур` распространилось на всю оперативную поверхность, а полная
Operational Reality скрылась за наличием Day Contract. Исправленная граница:
одно Operational Workspace содержит два явных представления — производную
`Рабочую реальность` и договорный `Рабочий контур`. Без договора пользователь
остаётся в реальности и может работать обычным образом. Вернуть внимание к
контракту система может по объяснимому расхождению с фактами, например по
неактуальному первому действию или работе вне договора; оценивать внутреннюю
управляемость пользователя по косвенным данным v1 не пытается.

## Ограниченный Context Probe

Риск дальней стратегии нужно проверить до строительства полной платформы.

Первый эксперимент ограничивается вручную запущенным Focus Session:

- один SourceNode;
- активное приложение и, при технической возможности, URL активной вкладки;
- постоянно видимый индикатор;
- мгновенная пауза и удаление;
- TTL не более 72 часов для сырого следа;
- сохранение только выбранных refs и краткого дистиллированного снимка;
- сравнение с ручным следом при возврате в дело и Track retrospective.

До первого реального автоматического наблюдения должны пройти gate: шифрование
чувствительных данных at rest, видимый индикатор, пауза, явные режимы
`purge-raw` и `forget-completely`, каскадное удаление производных записей,
аудит и защита от prompt injection. Screen content не входит в первый probe.

Эксперимент успешен, если он снижает время восстановления контекста или
добавляет полезное подтверждение результата при приемлемом уровне шума и
коррекций.

## Инкрементальная миграция

1. Существующие таблицы и API продолжают работать.
2. Ручные данные считаются первым каноническим источником.
3. Исторические переходы состояния и подтверждения постепенно получают
   append-only события.
4. Для внешних источников вводится общий observation envelope.
5. Operational Reality и отчёты читают существующие данные через адаптеры и
   новые события через одну проекцию.
6. Универсальная таблица всех событий не является предварительным условием.
7. Старые данные сохраняют явную provenance `legacy` или `inferred-current`.

## Готовность к синхронизации

Сейчас не требуется Hub или CRDT. Новые записи должны иметь стабильные UUID,
device provenance, идемпотентный ingest и отделённые `observed_at` /
`recorded_at`. Это сохраняет возможность будущего conflict-aware sync без
преждевременного строительства сервера.

## Метрики стратегии

- время возврата в дело после 1, 3 и 7 дней;
- доля актуальных Tracks с подтверждённым следующим шагом;
- доля заявленных результатов с evidence;
- доля машинных эпизодов, исправленных пользователем;
- полезные сохранённые факты на объём собранного сырья;
- выполнение решений предыдущих Reflection Sessions;
- время дневного и периодического обзора;
- число privacy/purge/revocation failures, целевое значение `0`.

## Не входит в первый слой

- always-on screen capture;
- полный Hub и multi-device sync;
- vector database как предварительное условие;
- автоматическая оценка продуктивности;
- молчаливое изменение Work Item или Track;
- полная миграция существующей базы на event sourcing;
- облачная зависимость.

## Открытые вопросы

- достаточно ли Work Item Event для state transition или нужен отдельный тип;
- как представлять несколько конкурирующих следующих шагов;
- когда подтверждённое машинное наблюдение становится долговременным фактом;
- как измерять полезность context probe без эффекта новизны;
- какие части синхронизировать первыми: canonical facts, настройки или blobs;
- нужен ли отдельный Intent/Commitment или достаточно Work Item + Decision.
