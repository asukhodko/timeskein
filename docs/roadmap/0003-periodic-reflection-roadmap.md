## 1. Целевой результат

Пользователь получает не просто экспорт времени за период, а рабочий контур саморефлексии:

- видно, куда фактически ушли силы;
- видно, какие треки получили реальное продвижение;
- видно, какие треки были шумом, реактивной суетой или recovery;
- видно, какие обязательства остались открытыми;
- видно, где следующий фокус действительно стоит защищённого окна;
- можно собрать фактуру для performance review;
- можно передать LLM структурированный пакет без ручной археологии по календарю, чатам и заметкам.

Главный принцип: сначала смысл результата, потом способ сбора контекста. Автоматические источники, скриншоты, активные окна и LLM-дистилляция добавляются только тогда, когда они улучшают ответ. Ручные фокус-блоки, события, refs и пользовательские мысли остаются достаточным первым слоем.

## 2. Пользовательские сценарии

### 2.1. Недельный обзор

В конце недели пользователь генерирует `weekly-review` и получает:

- итоги по дням;
- Work / Coordination / Recovery / Idle / Personal;
- топ Work Items;
- значимые gaps;
- captures и их исход;
- Day Events и Work Item Events;
- повторяющиеся источники переключений;
- 1-3 точки фокуса на следующую неделю.

Результат: решение, какие фокусы защищать, какие хвосты закрывать, что считать шумом.

### 2.2. Спринтовый обзор

Раз в две недели пользователь генерирует `sprint-review`:

- что было намерением спринта;
- какие треки реально двигались;
- какие были вытеснены встречами, инцидентами или операционкой;
- какие решения и артефакты появились;
- какие обязательства остались открытыми;
- что переносится в следующий спринт.

Результат: сопоставление планов с фактическим потоком работы.

### 2.3. Ретроспектива трека

Пользователь выбирает Track, например `Timeskein` или `Производственный процесс`, и получает:

- когда трек был активен;
- какие Work Items в него входили;
- сколько входов потребовалось;
- какие события, refs и captures связаны;
- где были паузы;
- что было результатом;
- что осталось следующим шагом.

Результат: история конкретного проекта без восстановления по памяти.

### 2.4. Performance review pack

Пользователь выбирает квартал и профиль `quarter-performance`:

- значимые треки;
- подтверждающие события;
- внешние refs;
- сложные кейсы;
- регулярные зоны ответственности;
- возможные формулировки вклада;
- предупреждения, где фактура неполна.

Результат: материал для организационного ревью, где факты отделены от интерпретаций.

## 3. Инкременты

### P0. Period Report CLI

Цель: получить первый отчёт за произвольный период без новой таксономии.

Что получаем:

- `pnpm report:period -- --from ... --to ...`;
- Markdown-отчёт;
- JSON-экспорт;
- группировки по дням, Work Items и Activity Zones;
- timeline за период;
- gaps;
- captures;
- Day Events;
- Work Item Events;
- предупреждения качества данных;
- секцию "что это говорит о фокусе".

Почему это первый шаг: он проверяет ценность периодического обзора на уже накопленных dogfood-данных. Не требует сначала проектировать Track/Label UI.

Готово, когда:

- можно сгенерировать недельный отчёт за реальные dogfood-дни;
- отчёт помогает выбрать 1-3 точки фокуса на следующую неделю;
- Markdown можно отдать в LLM без ручной склейки дневных отчётов.

### P1. Report Profiles

Цель: отчёты разных масштабов отвечают на разные вопросы.

Что получаем:

- `weekly-review`;
- `sprint-review`;
- `track-retrospective`;
- `quarter-performance`;
- блоки вопросов для LLM;
- шаблоны выводов и решений.

Готово, когда:

- недельный отчёт не выглядит как длинный дневной лог;
- квартальный отчёт выделяет фактуру вклада;
- спринтовый отчёт показывает намерение, факт и вытеснения.

### P2. Context Links and User Thoughts

Цель: будущий отчёт восстанавливает смысл, а не только длительность.

Что получаем:

- refs на Work Items и событиях становятся видимыми в отчёте;
- Work Item Events и Day Events явно помечаются как пользовательские мысли;
- capture-to-Work-Item сохраняет origin event;
- отчёт показывает "последний контакт с реальностью";
- внешние артефакты выводятся как evidence, а не как шум.

Готово, когда:

- по отчёту можно понять, почему Track считался актуальным;
- для значимого Work Item видны последний контакт, связанное событие и внешний ref;
- пользовательские мысли не теряются среди технической телеметрии.

### P3. Tracks and Labels

Цель: сделать срезы по смысловым трекам.

Что получаем:

- таблицы `tracks` и `labels`;
- основной Track у Work Item;
- labels на Work Item, событии или фокус-блоке;
- исторические snapshots Track/Labels на фокус-блоках;
- фильтры отчёта по Track, родительскому Track, label и Activity Zone.

Готово, когда:

- можно получить отчёт "только по Timeskein за месяц";
- можно получить отчёт "всё, что связано с performance-review";
- изменение Track сегодня не ломает исторический отчёт за прошлую неделю.

### P4. Operational Reality Panel

Цель: ответить на вопрос "что сейчас актуально и в каком состоянии?".

Что получаем:

- группировку active / waiting / blocked / stale-important / meeting-tail;
- состояние, уверенность и evidence;
- last touched;
- next action, если он есть;
- ручную правку состояния.

Готово, когда:

- пользователь видит живые незакрытые контуры;
- у каждого актуального пункта есть объяснение, почему он показан;
- можно быстро пометить done / waiting / blocked / not relevant.

### P5. Reflection Sessions

Цель: обзор периода заканчивается изменением рабочего контура, а не только чтением отчёта.

Что получаем:

- сохранённые выводы обзора;
- decisions;
- next focus points;
- связь выводов с созданными или обновлёнными Work Items;
- история обзоров.

Готово, когда:

- недельный обзор создаёт конкретные точки фокуса;
- можно открыть прошлый обзор и увидеть, какие решения были приняты;
- LLM-выводы не остаются потерянным текстом в чате.

### P6. LLM Pack and Redaction

Цель: безопасно отдавать LLM данные за период.

Что получаем:

- Markdown summary;
- JSON tables;
- список вопросов;
- warnings;
- redaction modes;
- сохранение ответа LLM как части Reflection Session.

Готово, когда:

- пользователь явно выбирает, что отдавать;
- можно скрыть внутренние URL, имена людей и чувствительные refs;
- LLM получает достаточно структуры для анализа без полного dump базы.

## 4. Первый рабочий срез

Первый срез должен быть маленьким:

```bash
pnpm report:period -- --from 2026-07-01 --to 2026-07-08 --profile weekly-review --format md
pnpm report:period -- --from 2026-07-01 --to 2026-07-08 --profile weekly-review --format json
```

В отчёт входят:

- summary;
- totals by day;
- totals by Activity Zone;
- totals by Work Item;
- significant gaps;
- captures and outcomes;
- Day Events;
- Work Item Events;
- data quality warnings;
- focus tuning questions;
- raw tables.

В отчёт пока не входят:

- автоматические SourceNodes;
- скриншоты;
- активные окна;
- умные inferred statuses;
- полноценные Track/Labels.

Это осознанное ограничение: сначала проверяем, что периодический обзор полезен на ручных данных.

---

## 5. Критерии успеха первой версии

1. Недельный отчёт генерируется без ручной склейки дневных отчётов.
2. Отчёт помогает выбрать 1-3 защищённых фокуса на следующую неделю.
3. Отчёт показывает, какие Work Items были шумом или реактивной работой.
4. Отчёт показывает recovery/gap-паттерны.
5. JSON можно отдать LLM, и она корректно понимает структуру периода.
6. Markdown можно сохранить в Obsidian как итог недели.
7. Отчёт явно показывает ограничения данных.

---

## 6. Что не делать первым

- Не начинать с фонового сбора окон и URL.
- Не строить UI Report Builder до проверки CLI.
- Не требовать обязательных Track/Labels для каждого Work Item.
- Не делать performance-review pack до недельного отчёта.
- Не пытаться автоматически оценивать "полезность" работы без evidence и человеческой проверки.

---

## 7. Следующее решение после P0

После первого недельного отчёта нужно ответить:

- хватает ли Activity Zones для смысловых срезов;
- какие Work Items хотелось сгруппировать в Track;
- какие labels реально нужны;
- какие refs отсутствовали для восстановления смысла;
- какие вопросы LLM смогла разобрать хорошо;
- где отчёт заставил снова вспоминать по памяти.

Только после этого стоит проектировать Tracks/Labels и Reflection Sessions.
